# 팀 회고

1. AI 가 만든 테스트를 '믿어도 되는가'를 판단할 때, 우리 팀이 가장 도움이 된 지표(또는 방법)는 무엇이었나요? (구체적 사례)
- 변이 점수가 가장 도움이 되었다. 테스트가 정상적으로 실행되고 통과하더라도 실제 결함을 잡아낼 수 있는지는 별개의 문제라는 것을 알게 되었다. 예를 들어 주문 취소 테스트에서 취소 상태만 확인하고 재고가 복원되었는지는 확인하지 않는 문제를 발견했다.

2. 줄 커버리지와 변이 점수가 다르게 나왔을 때 무엇을 배웠나요?
- 줄 커버리지가 높다고 해서 테스트의 품질까지 높은 것은 아니라는 점을 배웠다. 코드가 실행되는 것과 코드가 잘못되었을 때 이를 찾아내는 것은 다르기 때문에 줄 커버리지뿐만 아니라 변이 점수도 함께 확인해야 한다는 것을 알게 되었다.

3. 에이전트가 틀렸거나 약한 테스트를 만든 순간은? 우리는 어떻게 알아챘고 어떻게 바로잡았나요?
- AI가 작성한 테스트 중 실제 기능을 검증하지 않고 반환값의 존재 여부만 확인하는 테스트가 있었다. 예를 들어 환불 테스트에서 환불이 실제로 이루어졌는지 확인하지 않고 주문 객체가 존재하는지만 확인했다. 이를 발견한 후 환불 요청 횟수와 금액, 주문 상태까지 검증하도록 수정했다.

4. 불안정 테스트의 원인을 찾은 과정에서 가장 도움이 된 것은?
- 테스트마다 실행 환경과 데이터가 독립적으로 초기화되는지 확인하는 것이 가장 도움이 되었다. 특히 공유 상태나 실행 순서에 따라 테스트 결과가 달라질 가능성을 확인했고, Fake Clock과 Mock 객체를 활용하면 시간이나 외부 시스템에 의존하는 문제를 줄일 수 있다는 점을 배웠다.

5. AGENTS.md(규칙 파일)에 실습 중에 추가하거나 고친 규칙이 있다면?
- 테스트 간 독립성을 보장하고 각 테스트에서 필요한 데이터를 초기화하도록 규칙을 추가했다. 또한 테스트 이름과 실제 검증 내용이 일치해야 하며, 예외가 발생하는 상황에서는 반드시 오류 발생 여부를 확인하도록 수정했다. 추가로 커버리지와 변이 점수를 함께 확인하도록 규칙을 보완했다.

6. 다음에 AI 와 테스트를 만들 때 바꿀 점 한 가지는?
- 처음부터 AI가 작성한 테스트를 그대로 사용하지 않고, 테스트가 실제로 검증하는 내용과 놓칠 수 있는 결함을 먼저 확인할 것이다. 이후 변이 테스트를 통해 부족한 부분을 찾아내고 AI의 의견을 반영하여 반복적으로 개선할 것이다.

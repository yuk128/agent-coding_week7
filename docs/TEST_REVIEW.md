# AI 가 만든 테스트 리뷰 노트 (Mission 2)

대상: `ai_tests/*.test.js` (AI 도구가 생성했다고 가정). 기준: SRS · 계약서.
먼저 **측정**한다: `npm run coverage -- --tests ai_tests` 와 `npm run mutate:ai`. 그 다음 읽는다.

## 점검 체크리스트 (확인한 항목에 표시)
- [ v ] 단언이 값을 비교하는가? (`assert.ok(x)` · 존재 여부 · 길이만 확인하지 않는가)
- [ v ] 기대값이 독립적인가? (결과로 기대값을 계산하는 동어반복이 아닌가)
- [ v ] 경계값이 있는가? (최소 · 최대 · 딱 맞는 값 · 바로 바깥)
- [ v ] 오류를 제대로 확인하는가? (오류 코드까지 확인하는가, `try/catch` 로 삼키지 않는가, 오류가 안 나도 통과하지 않는가)
- [ v ] 테스트 이름과 단언이 일치하는가?
- [ v ] 테스트가 독립적인가? (한 테스트만 실행해도 통과하는가: `node scripts/test.js ai_tests --name "<테스트 이름>"`)
- [ v ] 계약서의 실패 경로 · 동시성 · 권한 규칙이 빠져 있지 않은가?
- [ v ] 같은 것을 반복하거나 구현 세부(저장소 내부 구조)에 묶여 있지 않은가?

## 발견한 결함
| # | 위치(파일 · 테스트 이름) | 결함 유형 | 왜 문제인가 | 어떤 결함(변이체)을 놓치는가 | 고친 방법 · 고친 테스트 |
|---|---|---|---|---|---|
| 1 | ai_tests(cancel.ai.test.js · 취소하면 재고가 복원된다) | 잘못된 검증 | 주문 상태가 CANCELED인지 확인할 뿐, 실제 재고가 복원되었는지는 확인하지 않는다. | 취소 처리 시 재고를 복원하지 않는 결함 | 취소 전후 상품 재고를 비교하고, 취소 후 재고가 주문 수량만큼 증가하는지 검증한다. |

| 2 | ai_tests(cancel.ai.test.js · 결제 후 취소하면 환불된다) | 불충분한 검증 | r.order의 존재 여부만 확인하므로 실제 환불이 이루어지지 않아도 테스트가 통과한다. | 환불 API를 호출하지 않거나 환불 금액이 잘못 계산되는 결함 | PG 환불 요청 횟수와 환불 금액, 주문 상태를 각각 검증한다. |

| 3 | ai_tests(cancel.ai.test.js · 환불이 실패하면 오류가 발생한다) | 예외 검증 누락 | try-catch 내부에서 예외를 잡기만 하고 아무런 검증도 하지 않는다. 환불이 실패해도 테스트가 성공할 수 있다. | 환불 실패를 무시하거나 주문을 정상 취소 처리하는 결함 | assert.rejects()를 사용해 오류 발생 여부를 검증하고 주문 상태와 재고도 확인한다. |

| 4 | ai_tests(cart.ai.test.js · 같은 상품을 다시 담으면 수량이 합산된다) | 잘못된 검증 조건 | 상품의 개수인 items.length만 확인한다. 실제 수량이 2개에서 5개로 합산되었는지는 확인하지 않는다. | 동일 상품을 추가해도 수량이 증가하지 않거나 기존 수량을 덮어쓰는 결함 | cart.items[0].quantity가 5인지 검증한다. |

| 5 | ai_tests(cart.ai.test.js · 수량 2개를 담을 수 있다, 수량 3개를 담을 수 있다, 수량 5개를 담을 수 있다) | 중복 및 검증 부족 | 세 테스트 모두 상품이 장바구니에 존재하는지만 확인한다. 요청한 수량이 정확하게 저장되었는지 검증하지 않는다. | 요청 수량과 관계없이 항상 1개만 저장하거나 다른 수량으로 저장하는 결함 | 각 테스트에서 cart.items[0].quantity가 각각 2, 3, 5인지 검증한다. |

| 6 | ai_tests(order.ai.test.js · 주문하면 재고가 차감된다) | 테스트 목적과 검증 불일치 | 테스트 이름은 재고 차감을 검증한다고 되어 있지만 실제로는 주문 ID와 상태만 확인한다. | 주문 생성 후 상품 재고를 차감하지 않는 결함 | 주문 생성 전후 재고를 비교하고 주문 수량만큼 정확하게 차감되었는지 확인한다. |

| 7 | ai_tests(payment.ai.test.js · 이미 결제한 주문은 다시 결제하지 않는다) | 멱등성 검증 부족 | 두 번째 결제 결과가 존재하는지만 확인한다. 실제 PG 결제가 중복으로 발생했는지 확인하지 않는다. | 이미 결제된 주문에 대해 PG 결제 요청을 다시 보내는 결함 | 첫 결제 후 PG 요청 횟수를 저장하고, 두 번째 결제 후에도 횟수가 동일한지 검증한다. |

| 8 | ai_tests(payment.ai.test.js · 결제가 실패해도 오류가 처리된다) | 예외 처리 검증 누락 | 결제 실패가 발생해도 catch 블록에서 아무것도 확인하지 않는다. 오류가 발생하지 않더라도 테스트가 통과할 수 있다. | PG 결제 실패를 무시하거나 주문을 PAID 상태로 변경하는 결함 | assert.rejects()로 오류를 확인하고 주문 상태가 결제 전 상태로 유지되는지 검증한다. |

## 팀의 결론 (3~5문장): AI 가 만든 테스트를 어떻게 믿을 수 있게 만들 것인가?
- 사람이 직접 설계한 내용을 바탕으로 부족하거나 개선이 필요한 부분을 AI에게 확인받는 과정을 반복하고, AI가 제시한 의견과 피드백을 검토하고, 실제 설계에 반영할 수 있는 부분을 선별한다.
반영한 내용을 다시 AI에게 전달하여 추가적인 문제점이나 보완할 사항이 있는지 확인하고, 이러한 과정을 여러 차례 반복하며 설계의 완성도를 점진적으로 높여나가야 한다.
최종적으로 사람의 판단과 AI의 의견을 적절히 결합하여 보다 효율적이고 완성도 높은 결과물을 도출한다.

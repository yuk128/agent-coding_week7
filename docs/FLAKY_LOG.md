# 불안정(flaky) 테스트 기록 (Mission 4)

측정: `npm run repeat -- flaky_tests/<파일>.test.js --times 30`

| 테스트 파일 | 수정 전 실패율 | 원인 가설 | 확인한 근거(어떻게 알았나) | 고친 방법 | 수정 후 실패율(30회 이상) |
|---|---|---|---|---|---|
| random_quantity.test.js | 20% (30회 중 6회 실패) | 수량을 1~11 중 시드 없이 무작위로 고르는데 P1 재고는 10이라, 11이 걸리면 재고 부족 예외가 난다 (시드 없는 난수) | npm run repeat 30회 실행에서 실패 예시가 모두 OUT_OF_STOCK(재고가 부족합니다)였다. 코드에서 무작위 범위가 1~11인 것과 재고 10을 대조했고, 예상 실패율(약 17%)이 측정값(20%)과 비슷했다 | Math.random()을 시드 고정 난수(mulberry32, 시드 20261106)로 바꾸고 수량 범위를 재고 이내인 1~10으로 제한했다. 경계값 1과 10을 직접 넣고 시드 난수 5개를 더해 7개 수량을 반복 검증한다. 단언(수량 기록, 합계 15000×수량)은 그대로 두고 실패 시 어떤 수량이었는지 메시지를 추가했다 | 0% (30회 중 0회 실패) |

| real_clock.test.js      | 23.3% (30회 중 7회 실패) | 실제 시계로 무작위 지연(jitter) 뒤에 30ms 경과를 판정해서, "방금 만든 주문"도 지연이 30ms 이상이면 이미 취소 대상이 된다 (실제 시간 경합) | 30회 중 7회 실패했고 실패한 테스트는 모두 "방금 만든 주문은 아직 자동 취소되지 않는다"였다. 코드에서 jitter가 0~40ms이고 기준이 30ms라서 약 25%로 예상했는데 측정값과 비슷했다. 첫 번째 테스트는 이번 30회에서는 실패하지 않았다 | 실제 시계와 sleep·jitter를 없애고 가짜 시계(createFakeClock)로 시간을 직접 조종한다. 30/60000분의 부동소수점 오차를 피하려고 경계에서 1ms 떨어진 31ms(취소됨)와 29ms(취소 안 됨)로 확인한다. 테스트 의도(30ms 지나면 취소, 안 지나면 유지)는 그대로다 | 0% (30회 중 0회 실패) |

| shared_state.test.js    | 50% (30회 중 15회 실패) | 두 테스트가 ctx 하나를 공유하면서 동시에(concurrency: true) 실행되어, 먼저 주문을 만든 쪽이 ORD-0001을 가져간다 (공유 상태 + 실행 순서 가정) | 30회 중 15회 실패했고 실패 예시는 기대 ORD-0001, 실제 ORD-0002였다. 코드에서 ctx가 파일 맨 위에서 한 번만 만들어지는 것과 describe의 concurrency 옵션을 확인했다 | 파일 공용 ctx를 없애고 테스트마다 createContext()로 새로 만들었다. concurrency: true와 jitter를 제거해 실행 순서 의존을 없애고, 두 번째 테스트는 첫 주문을 직접 만든 뒤 ORD-0002를 확인하도록 했다. 테스트 의도(주문번호 순차 발급)는 그대로다 | 0% (30회 중 0회 실패) |

## 원인 유형 정리 (팀이 직접 쓴다)
- 무작위 · 시간 · 실행 순서 · 공유 상태 · 외부 시스템 중 우리가 만난 원인은?
무작위	| 무작위 데이터나 실행 결과에 의존하는 코드는 확인되지 않음
시간   | 30분 경과 후 주문 자동 취소 테스트가 실제 시간에 의존할 가능성

- 앞으로 불안정 테스트를 예방하려고 AGENTS.md 에 추가할 규칙은?
새 테스트는 승인 전에 npm run repeat -- <파일> --times 30 으로 한 번도 실패하지 않는지 확인한다. 안정화를 이유로 단언을 약하게 하거나 테스트를 지우지 않는다.(근거: 한 번 통과한 것만으로는 불안정을 알 수 없다. R5 의 "일부러 실패시켜 보기"와 짝을 이룬다)


## CI 기준 (scripts/ci.js)
| 항목 | 기준값 | 근거(ai_tests 의 값 vs my_tests 의 값) |
|---|---|---|
| 줄 커버리지 | 90% | ai_tests 97.57% vs my_tests 90.91%. 줄 커버리지는 AI 테스트가 오히려 더 높아서 약한 테스트를 거르지 못한다. 그래서 "실행되지 않는 코드가 많은 변경"을 막는 최소선으로만 90%를 두었다. 우리 테스트(90.91%)가 이 선을 간신히 넘는 시점이라 여유는 크지 않았다 |

| 변이 점수   | 85% | ai_tests 58.2% vs my_tests 91.5%. 약한 테스트(58.2%)는 막고 우리 테스트(91.5%)는 통과시키는 사이값으로 85%를 정했다. 동등 변이체와 계약서에 없는 동작 때문에 못 죽이는 변이체가 있어서 100%를 요구하지 않고 여유를 두었다 |
